## 1. Overview

**Question the system answers:** which companies need cybersecurity software right now, why, and how do we reach
them first? **Output:** a ranked account list. Each account has `contact_score`, a `band`
(contact / review / skip / exclude), a plain-English `why`, and an optional outreach draft.

**Architecture:** medallion (bronze / silver / gold) with one script per stage. Rules do all scoring and banding.
The LLM touches only two things: judging the ambiguous `review` band, and writing text.

```
 BRONZE (raw, append-only, never modified)         D:\Cyber_DataSet\2026-09-14T10-00-00.json.zst  (12.36 GB compressed)
   data/raw/  (+ dev spread sample, section 10)    read in place by DuckDB, compression='zstd'
        |
        v   pipeline/1_clean.py        RULES  dedupe, type, parse dates, flag infra / noise
 SILVER  data/silver/hosts.parquet     grain: one row per host:port:transport
        |
        v   pipeline/2_companies.py    RULES  entity resolution (D4), unresolved report
 SILVER  data/silver/companies.parquet grain: one row per company
        |
        v   pipeline/3_signals.py      RULES  fit + urgency signals (deterministic SQL)
 GOLD    data/gold/signals.parquet     grain: one row per company (row count == companies)
        |
        v   pipeline/4_score.py        RULES  fit, urgency, contact_score, band, rule-based why
 GOLD    data/gold/accounts.parquet    grain: one row per account
        |
  ======|=========================== rules end here ====================================
        |   band = review only (a small share of accounts)
        v   llm/adjudicate.py          LLM (Haiku-class) via llm/client.py  -> contact | skip | needs_human + why
        |   band = contact (top N)
        v   outreach / email draft     LLM (Sonnet-class) via llm/client.py -> subject, body, signals_used
 GOLD    serving extract (small)       app-facing, derived, company level
        |
        v   app/streamlit_app.py       Streamlit Community Cloud, deploys from `prod`
```

Folder mapping is unchanged from CLAUDE.md section 6: bronze = `data/raw/`, silver = `data/silver/`,
gold = `data/gold/`. `data/` is gitignored and regenerated by the pipeline.

**Design principles (each is a rule in CLAUDE.md)**
1. Rules first. Scoring, banding, filtering and grouping are SQL/DuckDB/Python. No LLM import under `pipeline/`.
2. Precision over recall when grouping rows into companies. The unresolved share is reported, never hidden.
3. Every account has a `why` a salesperson can read. Rule accounts get a templated `why`; review accounts get
   the LLM `why`.
4. One script per stage. A wrong stage is rerun alone.
5. Every LLM call goes through `llm/client.py`, is traced, and is bounded by a cost ceiling.

Status: **proposal.** Under the `signal-engineering` skill the owner approves the list before `3_signals` is built.

unknown until stage 2 exists, and will probably be lower: the profile shows vulnerable rows concentrate on denylisted

### 3.1 Proposed FIT signals (is this our buyer)

| signal | source columns | meaning for a buyer | evidence in profile | failure mode |
|---|---|---|---|---|
| `in_territory` | `location.country_code` | company operates where we sell | US 50.95%, SG 18.78% (mostly Incapsula/Aceville, i.e. infrastructure), 160 countries | needs `icp.md`; IP country is the host country, not HQ |
| `named_registrant` | `identity_source` (org vs cert_o) | we can name the owner with evidence | org 99.83% populated; cert subject O 1.71% | cert O is often a default (Google Inc 153, Microsoft 76, Plesk 35, Acme Co 30) |
| `footprint_size` | `host_count`, `distinct_host_ips` (capped) | larger estate, larger deal | 66% of orgs have one row | weak size proxy; hosting providers dominate counts |
| `sensitive_stack` | tags `database`, `ics`, `medical`, `iot`; `product`, `os`, `cpe23` | holds data or systems that matter | `database` 99 rows, `iot` 181 | stack columns 78% to 98% null |
| `behind_waf` (later, v2) | `http.waf` on a resolved tenant | already buys security, so has budget and maturity | `http.waf` 11,495 rows, mostly CDN rows | WAF may be the CDN's, not the tenant's (D2) |
| segment / size / sector | not in the data | the owner's ICP segments | none | scan data has no headcount or revenue; segment fit must come from `icp.md` or a seed list |

### 3.2 Proposed URGENCY signals (do they need help now)

| signal | source columns | meaning | evidence in profile | failure mode |
|---|---|---|---|---|
| `kev_exposed` | `vulns[*].kev` | a known-exploited flaw is reachable | 1,819 rows (1.82%) | CVEs may be inferred from banner version (RAW-006) |
| `max_cvss_band` | `vulns[*].cvss` | worst severity on the estate | rows with CVSS 9.0+: 1,858; 7.0 to 8.9: 1,118; 4.0 to 6.9: 244 | median of row max is 9.8, so little spread; use bands, not raw value |
| `cert_expired_or_soon` | `ssl.cert.expired`, `ssl.cert.expires` | hygiene failure, visible to customers | expired 468; under 30 days 239 (of 7,910 cert rows) | 7.9% coverage; relative to scan time, which is fine inside one hour |
| `eol_stack` | tags `eol-product`, `eol-os` | running unsupported software | 1,527 + 23 rows, 512 distinct orgs | mostly nginx (1,288 rows); tag semantics set by the data vendor |
| `legacy_tls` | `ssl.versions` (no leading `-`) | SSLv2/3, TLS 1.0/1.1 offered | 1,384 rows | many hosts are CDN edges (infrastructure, removed upstream) |
| `risky_service_exposed` | `port` in 22, 3389, 445, 3306, 6379, 27017, 9200, 5900, 23, 2375 | admin or database service reachable | 22: 524; 3389: 96; 3306: 93; 445: 40 | port-level noise; port 12304 sweep (D3) must not leak in |
| `exposed_and_outdated` (combined) | risky port AND (`eol_stack` OR `max_cvss_band` high) | reachable AND weak, stronger than either alone | to be measured | needs company-level data to size |
| noise ratio (exclusion input) | tags `honeypot`, `c2`, `tor`, `compromised`; RAT modules | looks like attacker infrastructure, not a buyer | honeypot 679 rows; 739 rows with RAT modules | see "exclude band" note below |

Deliberately **not** used as signals:
- `timestamp`: the whole file is about 61 minutes (D3). No recency, no "new in last 30 days".
- EPSS: saturated (median 0.99957, 90th and 99th percentile 0.99999).
- `verified` on CVEs: 28 of 148,562 entries.
- CVE count: inflated by banner matching (rows with vulns average 46.1 CVEs, max 778); cap it.
- `asn` / `isp` / `cloud.provider`: they identify the provider, not the tenant; used only as exclusion flags.

### 3.3 How the score is built

- `fit_score` and `urgency_score`: each 0 to 100, each a weighted combination of the signals above. **Weights: to be calibrated.**
- `contact_score`: a function of fit and urgency. **Form: to be calibrated.** Candidates to compare on the real
  distribution: (a) weighted sum; (b) urgency gated by fit, so a very exposed company that is not our buyer cannot
  reach `contact`. The choice is made and justified at calibration, not now.
- Bands: `contact >= X`, `review` from Y to X, `skip < Y`, `exclude` by rule. **X and Y: to be calibrated.**
- `exclude` is a rule, not a score: a resolved company that fails an ICP rule (needs `icp.md`) or is dominated by noise hosts.
  **Open inconsistency to settle at M2:** D4 says noise rows never become companies, D2 says `exclude` holds
  "honeypot, C2, RAT" cases. Proposed resolution: noise hosts are dropped from company membership; a company whose
  hosts are mostly noise (share to be calibrated) is `exclude`.
- Rule-based `why`: a template that names the top one or two signals with their values, for example
  "3 hosts expose RDP; 1 CVE on the KEV list" (illustrative wording). Style rules: `account-scoring/references/why_style_guide.md`.

### 3.4 Calibration method (skill `scoring-calibration`)

1. Run `4_score.py` with provisional weights on the spread sample (D3). Port-based signals are calibrated on the
   spread sample only.
2. Run `score_distribution.py` for `fit_score`, `urgency_score`, `contact_score`.
3. Ask the owner for two inputs: sales capacity (accounts per week) and the per-run LLM budget. Size `contact` from
   capacity, `review` from budget, and set the edges by looking at accounts around each threshold by hand.
4. Preview thresholds with `--contact X --review Y` and a +/-5 sensitivity table.
5. The owner approves. Constants go into `pipeline/4_score.py`; weights, thresholds, band sizes and reasons are
   **recorded in this section afterwards**, and the owner fills CLAUDE.md section 12.
6. Never tune on the labelled eval examples and then report them as the score (section 6).

| contact_score formula | to be calibrated |
| contact threshold X / review threshold Y | to be calibrated |

## 4. Rule-vs-LLM split

| decision | rule or LLM | why |
|---|---|---|
| Parse, type, dedupe rows | Rule | Mechanical, testable, free. |
| Is this host infrastructure? | Rule (denylist families, `cloud.provider`, `cloud`/`cdn` tag) | Names come from a closed vocabulary; precision matters; an LLM would add cost and drift. |
| Is this row noise (honeypot, C2, RAT)? | Rule (tags, `_shodan.module`) | Explicit labels exist in the data. |
| Group hosts into companies | Rule (normalised name, D4 precedence) | CLAUDE.md: no LLM for grouping. Fuzzy matching only proposes candidates for review; it never merges. |
| Compute each signal | Rule (SQL) | Signals are facts from columns. |
| fit, urgency, contact score | Rule | Must be reproducible and calibratable on the distribution. |
| Band: contact / skip / exclude | Rule | Thresholds are tunable constants. Clear cases need no judgement. |
| Band: review (ambiguous middle) | **LLM, Haiku-class** | Weighing mixed evidence (strong urgency, weak fit; unclear owner) is judgement, and the band is small by design. Output is a classification with a JSON verdict, so the cheapest model that passes the evals. |
| `why` for contact / skip / exclude accounts | Rule (template) | The reason is the signal values; a template is exact, free and cannot hallucinate. |
| `why` for review accounts | LLM (same call as the verdict) | The verdict and its reason must agree; no extra call. |
| Outreach email / first touch | **LLM, Sonnet-class** | Writing quality matters; low volume (contact band, on demand or cached). |
| Follow-ups, sequence, subject lines | LLM, Sonnet-class (skill `email-writing`) | Same reason; optional, behind the first touch. |
| Check an LLM draft (length, banned phrases, grounding) | Rule (`validate_draft.py`, `lint_email.py`) | Grounding is a set-membership test against `signals_used`. |
| Validate LLM JSON | Rule (schema in `llm/client.py`) | Invalid output is never trusted. |
| Dev-to-prod gates | Rule plus human | Counts, contracts, eval deltas, cost. |
| Sector or company-type from page titles or domains | Not built (v1) | Tempting LLM use. Rejected: unproven precision, adds cost to 8M rows or 100K companies, and sits outside the review-band rule. Revisit only if evals show the review band needs it. |

What the LLM never does: grouping, scoring, thresholds, infrastructure flags, anything on `contact` or `skip`
accounts, anything on raw rows. This is the answer to "is each LLM use justified over a rule?".

## 5. LLM layer

### 5.1 `llm/client.py`: the only API gateway
- ALL model calls pass through it. No `import anthropic` anywhere else (checked by grep in every review).
- Entry points (proposed): one function per task shape, for example `classify(...)` for adjudication and
  `generate(...)` for drafting. Callers pass a prompt feature, version and variables; the client renders the file.
- Model per task is a constant in the client's config, not hard-coded in callers. Prices are a config table that
  `cost-report` fills from current published pricing, with a date.
- Secrets: the API key is read from the environment (`.env` locally, Streamlit secrets when hosted). `.env` is never
  read, printed or committed by agents.

### 5.2 Failure behaviour

| event | behaviour |
|---|---|
| Response is not valid JSON or fails the schema (`account-scoring/references/output_schema.json`) | Retry once, with the validation error in the retry prompt. Still invalid: `decision = needs_human`, never a guess. |
| Run cost reaches the per-run ceiling | Abort the run. Already-written results and traces are kept. The ceiling check happens before each call, using the worst-case cost of that call. |
| API error or timeout | Bounded retry with backoff counted against the ceiling; then `needs_human` for that account. Logged as a trace row with an error status. |
| Draft fails validation | Regenerate once with the problems listed; then `needs_human` (skill `outreach-draft`). |
| Hostile or legal reply in an email thread | Flag `needs_human` (skill `email-writing`). |

### 5.3 Trace schema: `traces/<env>.jsonl` (one JSON object per call, append-only, gitignored)

Required by CLAUDE.md section 8 (all must be present on every row):

| field | type | notes |
|---|---|---|
| `timestamp` | ISO 8601 string, UTC | call start |
| `request` | object | rendered prompt or messages plus parameters (`max_tokens`, temperature). Company data only; no personal data is in the pipeline inputs. |
| `response` | object / string | raw model output as returned, before validation |
| `model` | string | exact model ID used |
| `prompt_version` | string | for example `v2`, from the prompt file's front matter |
| `input_tokens` | int | from the API usage block |
| `output_tokens` | int | from the API usage block |
| `latency_ms` | int | wall clock of the call |
| `cost_usd` | float | computed from the token counts and the price table |
| `decision` | string | `contact`, `skip`, `needs_human`, or `draft` for text generation |
| `account_id` | string | the account the call was about |

Proposed additions (not required by CLAUDE.md; need `llm-engineer` agreement): `feature` (account_scoring /
outreach / email_writing), `env` (dev / prod), `run_id` (groups calls for the per-run ceiling and `cost-report`),
`attempt` (1 or 2), `status` (ok / invalid_json / error / ceiling_abort). Without `run_id` and `attempt` the retry
cost cannot be separated from the first-call cost.

One file per environment: `traces/dev.jsonl`, `traces/prod.jsonl`. Both are gitignored, so the trace itself is
not a repo deliverable; the repo will carry a small redacted sample under `evals/results/` or `outputs/` if the
owner wants graders to see real rows (open decision, section 14).

### 5.4 Prompt versioning
- Layout: `prompts/<feature>/vN.md`; features `account_scoring`, `outreach`, `email_writing`.
- Front matter on every file: `version`, `feature`, `parent`, `date`, `change` (template in
  `prompt-version/references/prompt_template.md`).
- A new prompt is a new file. Old versions are never edited or deleted. No prompt text in code. Placeholders
  (`{{icp}}`, `{{account_json}}`) are filled by the client; `{{icp}}` comes from `context/icp.md`.
- The JSON output contract in the prompt matches `output_schema.json`. Changing it needs a version bump and a validator update.
- Tool: `prompt_tool.py list | new | diff`. `llm-engineer` owns prompts, `qa-engineer` reviews. `prompts/account_scoring/`
  exists but is empty.

### 5.5 Model choice per task

| task | tier | why | upgrade rule |
|---|---|---|---|
| Review-band adjudication | Haiku-class | Binary verdict with a short reason; the review band is small | Move up a tier only if the eval shows the cheaper tier fails and the cost model still fits the ceiling |
| Outreach and email drafting | Sonnet-class | Writing quality drives reply rates; volume is small | Drop to the cheaper tier only if `validate_draft.py` pass rate and a human read hold up |

## 6. Evals

**What is evaluated:** the review-band adjudication (the core LLM feature). Drafting is checked by rules
(`validate_draft.py`, `lint_email.py`: schema, length, banned phrases, every claim in `signals_used`) and by human
reading; it has no precision/recall because there is no single right answer.

**Labelled set.** 20 to 30 accounts drawn from the **review band**, written to `evals/candidates.jsonl` with empty
labels by `sample_review_band.py`. Agents may add `suggested_label` with reasoning. **Only the owner sets `label`**
and moves rows into `evals/labeled.jsonl`. Agents never overwrite labels. `sales-team` output is never ground truth.
Draw stratified across the band (high-urgency/low-fit, low-urgency/high-fit, unclear identity, by `identity_source`)
so the set tests judgement, not the easy middle. Candidates cannot exist until M2 has produced a review band.

**Metrics.** Positive class = `contact`. Precision = TP / (TP + FP); recall = TP / (TP + FN); F1; the confusion
matrix; counts printed beside percentages. `needs_human` is counted as an abstention and reported as a coverage
rate, not hidden inside the other classes. Run cost from the trace file.

**Baselines.**
1. Previous prompt version: `python evals/run_eval.py --prompt vN --baseline vM` prints candidate and baseline
   metrics, flipped examples (fixed / regressed) and saves to `evals/results/` without overwriting earlier results.
2. Rules-only: the review band split at a single `contact_score` threshold (value chosen before looking at labels).
   If the LLM does not beat it, say so plainly; the cost of the LLM is then not justified for that band.
   Add trivial baselines (all `skip`, all `contact`) so precision and recall have context.

**Discipline.** Split the labelled set into a development part (used while writing prompts) and a hold-out part
(scored once per candidate version). Split sizes are a proposal for the owner, for example 15 / 10 of 25. Never tune a
prompt on examples and report those same examples as the score.

**Known weaknesses (stated up front).**
- n = 20 to 30: one flipped example moves a metric by 3 to 5 points (4 points at n = 25). Differences between prompt
  versions under about two flips are noise.
- One labeller; labels are judgement, not observed sales outcomes. The eval measures agreement with the owner.
- The review band is defined by the rule thresholds; recalibrating changes the population the eval was drawn from.
  Re-draw or re-validate after any recalibration.
- The eval exercises the verdict and `why`; it does not test the first-touch email beyond lint and grounding rules.

## 7. Cost model

Status: formulas only. **Prices are not quoted here.** They are "to be filled from current Anthropic pricing by
the `cost-report` skill, with the date". Token counts are **assumptions** until `traces/dev.jsonl` has real calls.

### 7.1 Formulas
```
cost per call   = (T_in x P_in + T_out x P_out) / 1,000,000        T = tokens per call, P = USD per million tokens
cost per run    = N_calls x cost per call
cost per month  = runs per month x cost per run
per-run ceiling = k x projected cost per run                         k = 2 proposed (cost-report template: "about 2x")
```

| task | model tier | N_calls per run | T_in (assumption) | T_out (assumption) | P_in, P_out |
|---|---|---|---|---|---|
| Review adjudication | Haiku-class | B = size of the review band | 900 | 120 | to be filled by cost-report |
| Outreach draft | Sonnet-class | C = contact-band accounts actually drafted (on demand or pre-generated) | 1,200 | 250 | to be filled by cost-report |
| Retries | same as above | about the invalid-JSON rate x B (unknown; measured from `attempt = 2` trace rows) | same | same | same |

T_in/T_out for adjudication are the illustrative figures in the `cost-report` and `scoring-calibration` skills;
those for drafting are my guess. Replace both with trace averages.

### 7.2 Worked example (placeholder inputs, clearly not measured)
The review-band size B depends on calibration (section 3.4) and is **not known**. Taking **B = 2,000 as a placeholder**
and the assumed token counts above:
- adjudication input tokens per run = 2,000 x 900 = 1,800,000; output tokens = 2,000 x 120 = 240,000
- cost per run = (1,800,000 x P_in,Haiku + 240,000 x P_out,Haiku) / 1,000,000
- with C = 100 drafts: input 100 x 1,200 = 120,000; output 100 x 250 = 25,000; cost = (120,000 x P_in,Sonnet + 25,000 x P_out,Sonnet) / 1,000,000
Plug in prices when `cost-report` fills them. The point of the example is the shape: adjudication cost is linear in B,
so band size is the budget lever, and drafting cost is linear in the number of drafts actually requested.

### 7.3 Levers
1. **Rules shrink the LLM input** to the review band only. Of an estimated 7.6M to 8.9M rows, the LLM never sees the infrastructure share (about 87% to 90% of rows in the sample), the `contact` band or the `skip` band. This is the main saving.
2. Calibrate the `review` threshold against the budget (scoring-calibration step 3).
3. Compact JSON input (signals and values only; no raw banners); cap `max_tokens`.
4. Prompt caching for the fixed ICP/context block if it is long enough to qualify; to be confirmed against current documentation.
5. Batch the non-urgent runs; **cache** adjudication and drafts keyed by (`account_id`, `prompt_version`, input hash) so reruns and the app never pay twice.
6. Pre-generate drafts for the contact band into the serving extract, so the hosted app needs no live calls by default.

### 7.4 Ceilings
| env | data | ceiling | enforced |
|---|---|---|---|
| dev | 100K spread sample | small; value set by the owner (to be decided) | `llm/client.py`, per run, abort when exceeded |
| prod | full scored extract | k x the projection from `cost-report` on real dev traces, approved by the owner | same code, different config |
| UI | interactive drafting | per-session cap (to be decided) | `llm/client.py` |

Review cadence: re-run `cost-report` after every prompt version and before every dev-to-prod promotion; record the
date and the prices used, because prices change.

## 11. Trade-offs, rejected alternatives and known weaknesses

### 11.1 Trade-offs and rejected alternatives

| decision | chosen | rejected | why |
|---|---|---|---|
| Medallion with files, not a warehouse | Parquet + DuckDB, one script per stage | Postgres / dbt / Spark | One machine, 8M rows, owner needs to re-run a single stage; no infra to host. |
| Rules vs LLM for scoring | Rules score; LLM only on review | LLM scores every account; embeddings similarity | Cost grows with 100K+ companies; unexplainable scores; cannot calibrate or reproduce. |
| LLM for grouping rows into companies | Deterministic normalisation (D4) | LLM or fuzzy matching merges | Precision first; an LLM merge is unreproducible and costs per row. |
| Infrastructure handling | Flag, keep rows in silver, never make companies (D1, D2) | Drop in `1_clean`; or keep vendors as competitor or channel accounts | Dropping loses the share report; vendor accounts would carry the tenants' exposure. |
| Tenant identity | `org`, then cert O; domains as evidence (D4) | Hostname/domain-first identity | Domain precision is unmeasured. |
| Recency | No time signal (D3) | Use `timestamp` | 61 minutes carries no "right now". |
| Dev data | Seek-spread sample | Head sample; reservoir over 84 GB | Bias; cost. |
| `why` | Template for rule bands, LLM for review | LLM `why` everywhere | Cost and hallucination risk for no gain. |
| Serving | Pre-generated drafts in a small extract | Live LLM calls per page view | Cost control; no secrets in the demo by default. |

### 11.2 Known weaknesses (candid)

1. **Low recall by design.** About 87% to 90% of rows are infrastructure and cannot be attributed to a customer. Only about 9.5% of head-sample rows (4,607 distinct orgs) can become companies. We list few accounts, with higher precision.
2. **The real exposure is invisible.** Vulnerable rows concentrate on hosting providers that are denylisted. The companies those hosts belong to are the people who most need the product, and the data cannot name them.
3. **No time signal.** About 61 minutes of one day. "Right now" is approximated by severity and hygiene (KEV, CVSS, expired certs, EOL, legacy TLS, exposed services), not by change over time. Nothing says whether an exposure is new or ten years old.
4. **Weak size signal.** 66% of orgs have one row. Host count mostly tracks how a company is hosted, not how large it is. There is no headcount, revenue, sector or contact data in the dump.
5. **Denylist long tail.** The list is 225 hand-picked exact names; the long tail is not covered. Prefix families and the `cloud`/`cdn` tag rule catch more but nothing proves the leak is zero. Mitigation: the leakage check and a by-eye read of the top 20 companies by host count.
6. **Domain-derived identity is unproven.** Up to 14% of infrastructure rows carry a non-provider domain in the probe, but that figure is an upper bound (provider-domain filter had 10 entries). If most are real, D4 under-resolves by about that much.
7. **CVEs may be inferred.** 877 rows share an identical old-CVE list; `verified` is on 28 of 148,562 entries. Signals use KEV and max CVSS, not counts, but a backported package still looks vulnerable.
8. **Evals are small and single-labelled** (section 6), and no eval exists until the review band does.
9. **Snapshot mismatch.** The brief's link is the 2026-10-08 snapshot; this project uses 2026-09-14. Numbers will differ on the other.
10. **Probe is not a random sample.** 9,239 rows from 21 windows, correlated within a window; per-window kept share ranged 3.6% to 20.2%.
11. **Business context is empty.** `context/business.md` and `context/icp.md` are blank, so `fit` and the D1/D2 buyer reasoning rest on the one-line brief, not a written ICP.
12. **Ethics and use.** Scan data describes exposure of named organisations. Outreach must not claim a breach or scare; drafts are suggestions and a human sends them (skill rules).
13. **Network-operator residual (DQ-002, D6.7).** ISP, hosting and telecom orgs that no rule names survive as companies: 20 of the top 50 orgs, 537 rows, on the spread sample (names only, one reviewer). Generic words (`network`, `internet`, `net`, `cloud`) cannot pass the 90% gate, and a hand list does not scale to the full file. Mitigation: gated operator words, named big providers, a possible M2 fit penalty and the `review` band; the top-50 read is repeated on the full run.

### D1. IBM, Oracle and Microsoft stay on the denylist
- **Context.** These three names belong to real enterprises. However, the `org` field holds the owner of the IP
  block, not the tenant. Microsoft Corporation has 722 rows in the head sample. In the probe, 57 of 61 Microsoft rows
  (93%) and 10 of 10 Oracle rows carry a `cloud`/`cdn` tag or a `cloud.provider` value. That makes them Azure and OCI
  tenant ranges. IBM had 11 rows in the probe, none cloud-tagged, which is negligible volume. All three also sell
  security products (Defender/Sentinel, IBM Security, OCI security), so they are not realistic buyers for a
  cybersecurity software vendor.
- **Decision.** Keep all three on the denylist. Treat their rows as infrastructure: no company is created from
  their `org` value. Change matching from exact to a normalised prefix family (`microsoft*`, `oracle*`, `ibm`,
  `ibm cloud`, `softlayer*`) so that variant spellings are caught.
- **Alternatives considered.** (a) Remove them and let them score as accounts. Rejected: at least 93% of the rows
  are cloud tenants, so the score would rate Microsoft on its customers' exposure and give a false `why`.
  (b) Keep only the rows without a cloud tag. Rejected for now: it gains at most one account (IBM, 11 rows) and
  adds a special case.
- **Consequences.** At most three real enterprise accounts are lost, which fits the rule of precision over recall.
  If the owner wants them as named accounts, add them by hand to a seed list, not through scan data.

### D2. Security vendors and website builders are excluded, not kept as channel or competitor accounts
- **Context.** Zscaler (513 head rows), Incapsula/Imperva (18,538 head rows, and 2,452 of 2,452 probe rows
  cloud/cdn-tagged), Palo Alto, Fastly, Cloudflare and Akamai operate proxy, edge or egress networks for their
  customers. Shopify, Squarespace, Wix, Vercel and Bitly host other people's sites and links (Bitly has 49 probe
  rows). Their `org` rows describe their customers' traffic, not their own estate. The output is a ranked list of
  **buyers**. A competitor or channel partner is a different list with a different `why`, and scan data provides
  no evidence for a partnership.
- **Decision.** Exclude both groups as infrastructure in the same way as D1, with
  `infra_reason = security_edge` or `website_platform`. Do not create channel or competitor accounts.
  In a later version, the fact that a *resolved* tenant sits behind a WAF/CDN (`http.waf` is set on 11,495 head rows)
  may be used as a fit or maturity signal. It is not an account.
- **Alternatives considered.** (a) Keep them as `exclude`-band accounts labelled "competitor". Rejected: their
  scores would be built from tenant exposure and would mislead anyone reading the list. (b) Keep them as channel
  accounts. Rejected: nothing in the data supports a channel motion, and it is outside the stated output.
- **Consequences.** The `exclude` band is reserved for resolved companies that fail an ICP or noise rule (honeypot,
  C2, RAT modules). Infrastructure never becomes a company, so it never appears in the account list. It is counted
  in the D4 report instead.

### D3. The head sample is not acceptable for development; switch to a seek-spread sample
- **Context.** The full file is a single hourly export of about 61 minutes on 2026-09-14. It is not a multi-day
  crawl. It moves forward in time by offset, is interleaved locally, and has port-sweep bursts of a few MB each.
  Org mix and infrastructure share are stable between the head sample and the probe (86.8% vs 85.7% denylisted).
  Port mix is not: port 12304 is 10.6% of the head sample but 1.7% of the probe. The head sample is the first 1.3%
  of the file and covers about 12 of the 61 minutes.
- **Decision.** Replace the dev sample with a **seek-spread sample**: 1,000 evenly spaced byte offsets with a
  fixed seed for jitter, taking 100 complete lines after each one, for 100,000 rows and about 1 GB read.
  This breaks up the port bursts (about 400 lines per 4 MB) and covers the whole hour. A data-integrator utility in
  `scripts/` builds it and writes a new file. The existing `sample_100k.jsonl` must not be modified. Only the owner
  places files under `data/raw/`, or must approve the target path, because CLAUDE.md says nothing writes to
  `data/raw/`. Keep the head sample for reproducing the existing profile.
  **Recency: the timestamp is dropped as an urgency signal for the whole dataset**, not only for the sample.
  Sixty-one minutes carries no "right now" information. Urgency comes from cert expiry, KEV/CVSS, EOL tags,
  legacy TLS and risky ports.
- **Alternatives considered.** (a) Keep the head sample. Rejected: it over-weights one port sweep and would bias
  every port-based signal and the score calibration. (b) A true uniform random sample (reservoir over about 8M rows).
  Rejected for dev because it scans all 84 GB. It is acceptable later as a one-off validation if the owner wants one.
  (c) Contiguous chunks of 10,000 lines. Rejected because each chunk inherits a burst.
- **Measured outcome (2026-10-11, spread sample `data/sample/spread_100k.jsonl`).** Infrastructure 85.75%, surviving 14.25%.
  Port 12304 is 218 of 100,000 rows (**0.22%**), not about 2%: the expectation was not reproduced, and the sample is
  less burst-prone than the probe, which is the intent of D3. Timestamps span 09:54:53 to 11:05:46, **about 71 minutes**, not 61: the
  file's hour is longer than the probe saw (the probe's last window ended 11:00:12). The expectations in the old text (86%, 10%, 2%)
  were therefore only matched for infrastructure. Nothing was stopped for this; the figures replace the estimates.
- **Consequences.** The profile was re-run on the spread sample before `1_clean`; see the measured outcome above. Signals that depend on port must be calibrated only on the
  spread sample. The prod run uses the full file. The 100K-row cost and DQ ceilings are unchanged.

### D4. Company identity: non-infrastructure `org` first, then cert subject O; hostnames are evidence only in v1
- **Context.** `org` is 99.83% populated, but about 86% of it is infrastructure. Tenant identity is scarce. Cert
  subject O is on 1.7% to 2.0% of rows, and on infrastructure rows it appears on only 105 of 9,239 probe rows (1.1%).
  Its top values there are defaults or vendor names: Google Inc 13, Huawei 7, Microsoft 6, Plesk 3, Acme Co 2,
  Default Company Ltd 2. Real tenants are rare (Bayerische Motoren Werke AG, 2 rows). Non-provider domains appear on
  up to 14% of infrastructure rows (1,292 probe rows). That figure is an upper bound because the provider-domain
  filter used had only 10 entries, and the precision of a domain as a company key is unmeasured. Reverse DNS on
  shared hosting names the host, not the owner.
- **Decision.** A row's identity is resolved in this order. The first rule that matches wins, and the source is
  recorded in `identity_source`.
  1. `noise`: tag honeypot/c2/tor/compromised, or a RAT/C2 `_shodan.module`. Never a company.
  2. `org`: normalised `org` (case, punctuation, legal suffix) that is not infrastructure. Infrastructure means a
     denylist match (exact, prefix, pattern or keyword) on the org text, OR a non-null `cloud.provider`, OR a
     `cloud`/`cdn` tag, OR the host IP matching a pattern CIDR. **The isp text is not used by itself** (D5).
  3. `cert_o`: the row is infrastructure **or its `org` is null** (amended by D6), and `ssl.cert.subject.O`, after
     normalisation, is not a default or vendor value and passes every denylist rule type including keywords (D6). A
     default-value list is needed: acme co, default company ltd, internet widgits pty ltd, plesk, plus the
     denylisted vendors.
  4. `infrastructure_unresolved`: the row is infrastructure with no usable tenant evidence. Kept in hosts, never a company.
  5. `null_org`: org is null (0.17%) and there is no cert O. Unresolved.
  When a non-infrastructure `org` and a cert O disagree, `org` wins and the cert O is stored as evidence.
  `company_id` is a stable hash of the normalised name, whichever source it came from, so `Fiserv` from org and from
  a cert merge into one company. Hostnames and domains are attached as evidence only in v1. Promoting them to rule 3b
  requires a check by data-quality-engineer: hand-review 50 random domain-derived tenants, with at least 90% being
  real, distinct companies.
- **Unresolved reporting.** `2_companies` prints, and writes to `outputs/dq/companies_<date>.md`, the row share and
  distinct host_ip share for each `identity_source`, plus the `infra_reason` breakdown (`cloud_provider`, `tag_rule`,
  `ip_pattern`, `org_exact`, `org_prefix`, `org_pattern`, `org_keyword`; the older category names hyperscaler, security_edge,
  website_platform, hosting and isp are no longer values). The shares must sum to 100%. The companies contract flags a resolved
  row share outside 5% to 20% (measured 14.25% on the spread sample). The same headline number ("about 86% of scanned services
  sit on shared infrastructure and cannot be attributed to a customer") goes into the README and the app footer.
- **Alternatives considered.** (a) `org` only. Rejected: it drops the few tenants we can prove from certs at no
  cost. (b) Tenant identity first (cert or hostname over org). Rejected: cert O is 98% null and polluted by
  defaults, and domain precision is unmeasured. Ranking it above a clean registry org lowers precision.
  (c) Treat domains as equal to cert O now. Rejected until the 50-row precision check passes.
- **Consequences.** Recall is low by design. About 14% of rows yield companies (spread sample), spread over 5,664 distinct orgs in
  100K rows. 66% of distinct orgs have a single row, so banner counts are a weak size proxy. The largest loss is
  the vulnerable estate on hosting providers (Aliyun 426, Amazon 255, DigitalOcean 97 vulnerable head rows): the
  exposure is real but cannot be attributed to an owner.

### D5. ISP field and denylist rule scope: the isp text never excludes a row by itself
*Decided by senior-data-engineer under the owner's delegation, 2026-10-11. Status: decided; the owner may overrule.*
- **Context.** In Shodan data `org` is the registrant of the IP block and `isp` is the upstream network. Matching the denylist on
  `isp` as well as `org` excluded 3,516 rows (798 distinct non-null orgs, plus 50 null-org rows) of the spread sample whose org
  alone would survive. Gate: a names-only review of 50 of those orgs (the 25 largest, then 25 from a seeded shuffle, UNSURE counted
  as real) found **22 of 50 (44%) infrastructure against a 90% threshold: FAILED** (`outputs/denylist_cleanup_review.md` section 3.3).
  The five largest, 1,293 rows, are real companies: Egnyte 331, Fiserv 329, Wal-Mart 246, Avago 239, TGS Management 148,
  all with isp `google`. The open question was whether an isp-only rule limited to hyperscaler/CDN isp names (google, amazon com,
  cloudflare, ovh, fastly) should be kept.
- **Evidence for that question** (read-only, spread sample, rows whose org survives and whose isp is one of those names):
  1,963 rows, 169 distinct orgs, 1,216 distinct IPs. By isp: google 1,683 (58 orgs), ovh 94, amazon com 88, cloudflare 62, fastly 28,
  akamai 4, oracle 3, digitalocean 1. Tenancy evidence is almost absent: 1 row of 1,963 has a provider reverse-DNS or domain
  (`googleusercontent.com`, `amazonaws.com`, `cloudfront.net`, ovh/fastly/cloudflare names; the one is a person-named org);
  0 of the 1,683 Google-isp rows carry any tag (the group is defined as rows that pass the tag and `cloud.provider` rules, and none of the Google-isp rows has a tag at all);
  0 of them have a vulnerability (the group's 14 vulnerable rows are all non-Google); 278 of them (16.5%) have hostnames, and for
  Wal-Mart all 246 rows resolve to `walmart.com`. The top 5 Google-isp orgs hold 1,293 rows across 82 to 169 distinct IPs each, on
  scattered high ports, with no product fingerprint: the pattern of an organisation's own address block announced through a
  Google network, not of a workload on a Google Cloud address. Among the non-Google isp rows, most are mixed: Adobe on its own
  `adobedc.net` names (30 rows), GitHub behind Fastly (28), Zendesk and Webflow behind Cloudflare, and several OVH affiliates
  (OVH Singapore 17, OVH Hispano 9, OVHTECH 7, OVH NWK 6, OVH BE 5) that are infrastructure by org name.
- **Decision.** Keep `isp_matching="ignore"`. Do not restore any isp-only rule, narrow or partial. Infrastructure is: a denylist
  match (exact, prefix, pattern or keyword) on the org text, OR a non-null `cloud.provider`, OR a `cloud`/`cdn` tag, OR the
  host IP matching a pattern CIDR. The OVH affiliates are an org-name gap and are fixed on the org side (below), not via isp.
- **Why not a partial restore on provider reverse-DNS.** It would remove 1 row of 1,963, so it is not worth a rule. The tag and
  `cloud.provider` rules already catch the hosts that really are cloud tenants.
- **Cost of being wrong.** If we are wrong to ignore: the Google-isp customers (58 orgs, 1,683 rows) are in the list although their
  address space is Google Cloud tenancy. Effect: some accounts have a `why` built on hosts that belong to a Google Cloud project; the
  IP block is still registered to that customer, and the group has 0 vulnerable rows, so no urgency is claimed from it. A salesperson
  contacts a real company with imperfect attribution. If we restore the rule and are wrong: 58 real companies (Egnyte, Fiserv,
  Wal-Mart, Equifax, ...) vanish silently, recall falls further on a list that already keeps only 14%, and the loss is invisible
  because excluded rows only appear in a count. Precision is protected by the tag rule either way. The second error is worse
  and less visible, so the choice is ignore.
- **Alternatives considered.** (a) Restore the isp rule for the five names. Rejected: no tenancy evidence in 1,963 rows,
  and 1,683 of the rows are Google-isp customers. (b) Restore on reverse-DNS evidence only. Rejected: 1 row. (c) Keep isp matching
  for all names. Rejected: gate failed 44% against 90%.
- **Org-side follow-ups (integrator, gated as before).** `ovh` is under 4 characters so it is exact-only; OVH affiliates survive. Test
  an org-scoped keyword `ovh` through the usual 90% gate before adding it. Webflow (10 rows, one IP) fits D2 (website builder);
  the owner must approve adding it, as with weebly, jimdo, automattic and tumblr.
- **Consequences.** Infrastructure 85.75%, surviving 14.25% (14,253 rows, 5,664 distinct orgs), up from 89.40% / 10.60% before
  the cleanup. 1,026 of 3,076 vulnerable rows (33.4%) sit on surviving rows. The 3,516 released rows carry 120 vulnerable rows, so
  most of the gain is non-urgent. `exclude` mode stays in code only to reproduce old counts.
- **Known weakness.** The denylist is validated by a names-only review by a single reviewer on a 100K sample, with UNSURE counted
  as real and no external lookup. The 22/50 result is far enough from 90% that this does not change the decision, but every
  denylist rule that passed its gate carries the same limit, and `check_contract.py` still enforces none of the prefix, pattern or
  keyword rules (RAW-010). The tenancy-versus-own-estate reading of the Google-isp group is inferred from the registrant, hostnames and
  port patterns; it was not confirmed by any external lookup (WHOIS, BGP) or by the customer.

### D6. hosts layer (1_clean) choices
*Decided by senior-data-engineer under the owner's standing delegation ("when in doubt, the senior decides"), 2026-10-11. Status: decided; the owner may overrule. Evidence: `pipeline/1_clean.py` output on `data/sample/spread_100k.jsonl` (97,758 hosts rows), `outputs/dq/hosts_review_2026-10-11.md`, ISSUES RAW-006/007/013, PIPE-001..003, DQ-001..004. Read-only measurements; nothing was rerun.*

**D6.1 Noise modules**
- **Context.** `is_noise` = tag honeypot/c2/tor/compromised, or a module ending in `rat`. 1,089 noise rows. The loose suffix rule would also catch unrelated names, and DQ-004 reports 185 backdoor-module rows outside it: `njrat78` 2 rows, `xiaongmai-backdoor` 183 rows.
- **Decision.** Replace the suffix rule with the explicit pattern `(^|-)rat$|^njrat$|^blackshades$`. Noise rows 1,089 to 1,136. Do NOT widen to `njrat78` or `xiaongmai-backdoor`. **DQ-004 is closed "by design":** `njrat78` is 2 rows on Meta cache nodes (a banner artefact); `xiaongmai-backdoor` is 183 rows over 25 orgs, port 9530, a fact about a DVR device family affected by a backdoor, with 7 rows on real orgs. The host is a victim or a vulnerable device, not attacker infrastructure, and that is useful urgency evidence for a security seller. Dropping it from company membership would hide the finding. `blackshades` is 47 rows on port 4444, 1 real org (included).
- **Alternatives.** Keep the suffix rule (rejected: matches by accident); match `rat` or `backdoor` anywhere (rejected: removes real victims).
- **Consequences.** 47 more rows become noise. Module-name rules are a closed, explicit list; new RAT families are added by decision, not by pattern. The contract rule "noise implies tag or RAT module" must use the new pattern.

**D6.2 `vuln_count`**
- **Decision.** Capped at 50, informational only. Signals use `max_cvss` and `has_kev`, computed before capping. **Why.** CVE lists look banner-inferred (RAW-006; average 46.1, max 778). **Alternative:** drop the count (rejected: cheap context for `why`). **Consequence:** no score weight on the count.

**D6.3 Certificate dates**
- **Decision.** Values outside 1990..2100 stay nulled; add `cert_date_invalid` BOOLEAN (true when either date was present but rejected). A 1970 issue date (24 of the 26 bad issued values) is not a v1 signal. `cert_expired` (raw boolean) is kept as delivered and may disagree with a null date. **Alternative:** treat 1970 as a "device without clock" signal (rejected: 24 rows, no evidence it predicts need). **Consequence:** the cert-expiry signal in section 3.2 uses `cert_expired` and `cert_expires` only where valid.

**D6.4 cert_o rule, name guard and DQ-001**
- **Context.** `cert_o` rows: 644 rows, 432 distinct names (0.66% of hosts), 637 on infrastructure rows and 7 on null-org rows. D4 rule 3 said "the row is infrastructure"; the implementation also takes null-org rows, which is right (a null org with a usable cert O is as good as an infrastructure row). Most cert_o names are real tenants (Accenture 20, Okta 7, Datadog 6, SAP 6, Salesforce 6, Royal Bank of Scotland 5). - **Decision (DQ-001).** (a) Amend D4 rule 3: cert_o applies when infrastructure OR org is null (done above). Keyword rules were gated on org text, so the cert-text gate is: every distinct cert O newly matched by a keyword is hand-reviewed at the first full run (up to 50 names, at least 90% infrastructure or operator), reported in `outputs/denylist_*`. On the spread sample the new hits are 3 names, 3 rows, all telecom operators (3 of 3, too few to be a real gate, so the full-file review is the gate). (c) Add a small device-vendor / operator cert list to `context/cert_default_names.txt` as exact normalised names: `huawei`, `huawei technologies`, `huawei software technologies`, `sierra wireless`, `ruckus wireless`, `aruba networks`, `arista networks`, `mitel networks`, `technicolor`, `rakwireless`, `comcast`, `ntt docomo business`, the China Telecom Cloud name (`天翼云科技有限公司`) and `dis`, plus the name guard `meta platforms`, `facebook`, `apple`, `netflix` (own-estate names that sit on CDN or cache-node ranges). `dis` is ambiguous and is listed on the evidence that it is 7 rows on 3 orgs with no company identity; the data-integrator may drop it if a look at the rows shows a tenant. Org-side prefixes `facebook`, `meta platforms` and `netflix` go through the 90% review before they are added to the denylist. (d) A cert_o company is weaker than an org company, and that is accepted: it is 0.66% of rows. **Alternative:** accept keyword hits as tenants (rejected: the contract and CLAUDE.md say no ISP names as companies, and the hand list needs no scaling at this volume). **Contract assertion (cleanest, does not weaken it):** keep `denylist: {column: name_norm, rules: shared}` unchanged with 0 hits allowed; it now passes by construction because the stage applies the same matcher. **D6.7 DQ-002: ISP, hosting and telecom orgs that survive as `identity_source='org'`**
- **Context.** In the top 50 orgs, 20 orgs / 537 rows read as network operators (China Unicom Henan province network 51, Uninet 37, ANTEL 36 and 33, Web.com 29, RackNerd 28, PSINet 27, NTT America 26, IONOS 26, Vodafone 25, Comcast IP Services 24, Fastweb 23, CloudFly 23, Telstra 20, EGIHosting 20, webhosting servers 20). The matcher is correct; no rule covers them (RAW-013 residual). Org rows are 13,755 rows over 5,504 distinct names. Whole-word probes on `name_norm` of org rows, rows / distinct names: `unicom` 247 / 39, `province network` 202 / 30, `network` 688 / 271, `internet` 462 / 214, `communications` 342 / 140 (this word already failed the gate at 78.0%), `net` 212 / 99, `cloud` 192 / 70, `mobile` 66 / 26, `vodafone` 90 / 19, `ntt` 63 / 8, `telstra` 24 / 2, `comcast` 27 / 3, `host` 34 / 20, `servers` 77 / 24. The generic words are mixed with real companies and cannot pass a 90% gate; only the distinctive operator words can.
- **Decision.** Do not chase the long tail by hand. For v1 (a) run these candidates through the existing org-scoped 90% gate and add the ones that pass: `org: unicom`, `org: province network`, `org: web hosting` and `org: hosting` as a substring variant (to catch EGIHosting) if its review passes. (b) Add exact or prefix entries only for named big providers seen in the review list with at least 20 rows (Telstra, Comcast, Vodafone, NTT America, IONOS, RackNerd, Web.com, PSINet, Fastweb, Uninet, ANTEL); they fit the D1/D2 families, are reviewed once, and are cheap. (c) Accept the remaining residual as a documented known weakness (section 11.2, item 13), to be measured and reported on every run, and let M2 handle it: stage 4 may add a fit penalty for network-operator-looking names (name-shape flag derived from the gated words), and ambiguous cases fall into the `review` band, where the LLM sees the `why`. No rule is added only to make a check pass.
- **Cost of each error direction (sales use case).** A missed operator (false company) puts a telecom or host on the list with the exposure of its customers in the `why`: a rep wastes a touch and the list loses credibility, but it is visible and the review band catches some. A wrongly removed real company vanishes silently, and the list already keeps only about 14% of rows. Precision is the stated priority (CLAUDE.md), so a gate at 90% is kept; but because the second error is invisible, no generic word (`network`, `internet`, `net`, `cloud`) is added.
- **Scale.** On the full file (about 7.6M to 8.9M rows, estimated) the operator long tail is thousands of names; a hand list will not scale, and nothing here claims it does. Measure the residual with the same top-50 read on the full run and report the count; if it is above 10% of the top 50, reopen with a data-driven approach (ASN-level or name-shape rules, owner decision).
- **Consequences.** Denylist coverage improves a little (about 50 to 100 rows of the 537 on the sample if all candidates pass; not measured), the weakness stays named, and the contract cannot catch an unlisted name.

  correlated. Per-window kept share ranged from 3.6% to 20.2%.

  task brief ("cybersecurity software company"), not on a written ICP.
- The domain-based tenant share (up to 14%) is an upper bound with an unknown precision. If it is mostly real,
  D4 under-resolves by about that much.
